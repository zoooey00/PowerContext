# 可重复验收样例

## A. 真实 Dify 三会话玩法（待在工作区执行）

初始条件：按 README 启动网关及 PowerContext，导入唯一 DSL、绑定有效模型、配置环境变量并发布。使用同一 Dify Web App 浏览器身份；新建存档名，例如 `judge-当天时间`，不能复用已经玩过的存档。无知识库或预置数据。

| 顺序 | 操作及输入 | 必须观察到的表现 |
| --- | --- | --- |
| 1 | 新建聊天，填存档名；发送 `恶作剧：会打嗝的月亮` | 召回为空；模型描述第一次恶作剧；收据第 1 回合，警惕 2/5、交换价 7；保存节点返回真实 Memory Artifact 引用 |
| 2 | 新建另一个聊天，仍用相同存档名；发送 `交换：一双失眠的拖鞋` | 召回里出现“会打嗝的月亮”；模型回扣月亮；收据第 2 回合，警惕 2、交换价 7 |
| 3 | 再新建聊天，相同存档名；发送 `道歉：一颗薄荷糖` | 召回里有月亮和拖鞋；模型接受赔礼；收据第 3 回合，警惕 1、交换价 5 |
| 4 | 新建聊天，改用全新存档名；发送 `看看：柜台` | 没有之前玩家经历；第 1 回合，警惕 0、交换价 3 |

第 2 步必须是独立 conversation_id，否则不能证明跨会话。模型措辞没有唯一答案，但不得把没有发生的细节当成记忆；规则以收据为准。如模型未引用召回物品，应保留失败记录检查提示与模型，不能把手写台词充当实际回复。

自动方式：`verify_dify.py` 每次生成新 end-user，确保空档，执行前三步并检查三个不同 conversation_id。该脚本需要已发布的 Chatflow API Key。成功才输出 `evidence/dify-live.json`。当前未生成此证据。

保存证据：

1. Dify 导入成功界面与工作区实际版本。
2. 模型供应商名称、插件版本和选定模型（隐去凭据）。
3. 第 1 次召回空记录、第 1 次保存 HTTP 200 与返回引用。
4. 第 2 次召回中具体物品、送进 LLM 的 context、第 2 次回复及收据。
5. 第 3 次道歉后的价格。
6. 发布后的实际 Web App 入口；如仅本地运行，明确入口只在配置环境内可用。

重置：每次更换角色存档名或 API end-user，无需手动修改数据库。旧数据保留，可供复查。

## B. 已执行的真实 PowerContext 后端验证

命令：`python verify.py`（在安装完成的虚拟环境中）。环境、时间、请求、实际写入返回、独立 Artifact 引用和召回正文保存在 `evidence/backend-run.json`；服务级读写日志在 `evidence/services.log`。

结果：空档 → 恶作剧后价格 7 → 重启 PowerContext 进程 → 召回月亮、价格仍 7 → 不同用户空档、价格 3 → 交易成功 → 拒绝旧票据 → 道歉后价格 5。另验证同一票据重复提交不会新增回合，以及无效 token 返回 401。

脚本使用固定“测试台词”，用于把记忆与规则验证从模型的随机输出中分离。**它没有导入 Dify、没有执行 LLM，不能代替样例 A 或作为完整验收已通过的证据。**

## C. 故障体验

停止网关后在 Dify 发送消息，应报 HTTP 连接失败，不输出“记忆已保存”。恢复网关后新发行动。模型服务不可用或 Key 无效时，应停在模型节点，不触发记忆写入。以上 Dify 故障样例同样待在真实工作区验证。
